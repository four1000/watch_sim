## 6-1 Navigator：畫面堆疊

[navigator.cpp](../../../../ap/src/ui/navigator.cpp)：固定深度 6 的堆疊（[navigator.h:13](../../../../ap/include/ap/ui/navigator.h#L13)），只存指標（**借用**畫面）。

| 操作 | 行為 |
|---|---|
| `push(s)` [L5](../../../../ap/src/ui/navigator.cpp#L5) | 舊頂層 `exit()` → 推入 → 新畫面 `enter()`。滿了或已經在堆疊裡就拒絕 |
| `pop()` [L13](../../../../ap/src/ui/navigator.cpp#L13) | 至少保留一層（錶面） |
| `resetTo(root)` [L21](../../../../ap/src/ui/navigator.cpp#L21) | 清空，只留 root |
| `popUntil(s)` [L29](../../../../ap/src/ui/navigator.cpp#L29) | 一直 pop，直到 s 成為頂層 |

它同時也是責任鏈的第 ③ 環（第 3 課）：先交給頂層 Screen，沒人處理而且是 BACK 短按，就 pop。

## 6-2 Mediator：ActivityFlowCoordinator

問題：活動狀態改變時，該顯示哪個畫面？這條規則該放在哪裡？
- 放在 Session？那 Session 就得認識畫面，違反分層。
- 放在各畫面？規則會散落各處。

答案：放在一個專門的中介者裡，見 [activity_flow.h:22](../../../../ap/include/ap/ui/activity_flow.h#L22)：

```cpp
void onEvent(const Event& e) override {          // 只訂閱 ActivityStateChanged
    switch (c.to) {
        case Ready:   m_nav.push(m_data, t); break;                          // 進資料頁
        case Running: if (c.from == Paused) m_nav.popUntil(m_data, t); break; // 恢復：回資料頁
        case Paused:  m_nav.push(m_pause, t); break;                          // 推暫停選單
        case Idle:    m_nav.resetTo(m_home, t);                               // 回錶面
                      if (c.outcome == Saved) { m_summary.select(0); m_nav.push(m_summary, t); }
    }
}
```

Session 和畫面**互不認識**。要改 UX（例如「存檔後顯示摘要」）只動這一個類別。

## 6-3 NVI / Template Method：所有畫面有一致的外框

[screen.h:16](../../../../ap/include/ap/ui/screen.h#L16)：

```cpp
void render(ICanvas& c, const UiModel& m) {     // 非虛擬：流程固定
    c.clear(Color::Black);
    onRender(c, m);                              // 子類別只填這個 hook
    if (showsStatusBar()) drawStatusBar(c, m, showsClock());
}
protected:
    virtual void onRender(ICanvas& c, const UiModel& m) = 0;
    virtual bool showsStatusBar() const { return true; }
```

`enter()`、`exit()`、`handle()` 也一樣，公開介面非虛擬，客製化放在 `onEnter`、`onGesture` 這些 hook。新畫面不可能忘記清屏，也不可能忘記畫狀態列（GPS 點、心率點、鎖定 L）。

## 6-4 View-model snapshot：畫面只讀快照

[ui_model.h:12](../../../../ap/include/ap/ui/ui_model.h#L12)：`UiModel` 是純資料（時間、活動快照、心率、zone、設定、鎖定、背光）。每次 render 前由 `buildModel()` 填好，畫面**只讀它**。

- **渲染不可能改變狀態**：畫面拿到的是 `const UiModel&`。
- **畫面可以獨立測試**：填一個 struct 就能測，見 [ui_test.cpp](../../../../tests/ui_test.cpp)。
- **可以跨核心**：快照可以整份交給另一個 UI task。

例外是歷史紀錄：資料量太大，不適合放進快照。歷史畫面拿的是**唯讀**的 `const IActivityHistory&`，用 `activityAt(i, out)` 一次 copy-out 一筆到呼叫者的 struct，不會拿到指向儲存體的指標。同一個 `ActivityDetailScreen`（[screens.h:106](../../../../ap/include/ap/ui/screens.h#L106)）同時服務「剛存檔的摘要」和「從歷史點進來」。

## 6-5 Decorator + Adapter：主題和顯示硬體

```
Screen::render ──▶ ThemedCanvas（Decorator）──▶ ICanvas ──▶ OpenCvCanvas（Adapter）──▶ OpenCV
```

- **ThemedCanvas**（[themed_canvas.h:31](../../../../ap/include/ap/ui/themed_canvas.h#L31)）：背光開啟時改成白底深色字。它包住真正的 canvas，每個繪圖呼叫都先經過 `themed()`（[L12](../../../../ap/include/ap/ui/themed_canvas.h#L12)）換色：Black↔White，Yellow→Orange（黃色在白底上看不見）。**畫面完全不知道主題存在**，加夜間紅光模式只要改一個對照函式。它是 render 時才建立的 stack 物件，沒有 heap。
- **OpenCvCanvas**（[opencv_canvas.h:9](../../../../platform/sim/opencv_canvas.h#L9)）：把 `ICanvas`（[canvas.h:18](../../../../ap/include/ap/ui/canvas.h#L18)）轉成 OpenCV 呼叫。換成真的 LCD driver，只要換這一層。

## 6-6 完整追蹤：跑步中按 START

（對照 [architecture.md §3](../../../../docs/architecture.md) 的 sequence diagram）

```
① 按鍵執行緒  postKey(START Down/Up)           → 加鎖進 inbox            [第 2 課]
② step()      drainInbox → GestureRecognizer  → START Short              [第 3 課]
              publish(Gesture)
③ dispatch    WatchApp::onEvent → router.route                           [第 4 課]
              KeyLock：沒鎖，放行 → Overlay：沒 modal，放行 → Navigator
④ Navigator   → 頂層 ActivityDataScreen.handle → control.startPause(t)
⑤ Session     RunningState::startPause → metrics.pause → transitionTo(Paused)
              publish(ActivityStateChanged Running→Paused)               [第 5 課]
⑥ 同一個 dispatch 迴圈，下一個事件：
              Coordinator → nav.push(暫停選單)                           [本課]
              Overlay     → vibrate(Double)
              HrZoneMonitor → 不是 Running，重置警示
⑦ render()    buildModel → ThemedCanvas → 暫停選單.render → overlay.render
```

能把這 7 步講順，就代表你掌握了整個專案的 workflow。

## ⌚ 對應真實手錶
真實手錶多半是 MIP 反射式螢幕，需要部分更新，frame buffer 也有限制。snapshot、Decorator、Adapter 讓「畫什麼」和「怎麼送上螢幕」解耦，換顯示硬體或加省電的局部更新，都不會影響畫面邏輯。

## 📝 小測驗
1. 為什麼畫面不直接讀 ActivitySession，而要經過 UiModel？
2. 如果要加一個「夜間紅光模式」，要改哪裡？
3. `Screen::render` 為什麼不是 virtual？

<details>
<summary>參考答案</summary>

1. 讓渲染沒有副作用、畫面能獨立測試，未來也能把快照交給另一顆核心或 UI task，不需要共享鎖。
2. 新增一個 Theme 值和對應的色表（`themed()`），render 時選用它。畫面都不用改。
3. 這是 NVI：基底類別控制固定流程（清屏 → 內容 → 狀態列），子類別只能覆寫 hook，就不會有畫面忘記畫狀態列或順序錯亂。
</details>

## 🎤 面試追問
<details>
<summary>Mediator 和 EventBus 都在解耦，差在哪裡？</summary>

EventBus 是通用的訊息管道，不含業務規則。Mediator 是**擁有規則**的協調者，「哪個狀態對應哪個畫面」集中在它身上。Coordinator 是透過 bus 收到狀態變化的，兩者是搭配使用的。
</details>

<details>
<summary>Navigator 為什麼拒絕 push 已經在堆疊裡的畫面？</summary>

畫面物件只有一個實例（被借用的成員）。同一個實例出現兩次，enter/exit 的配對會錯亂，pop 時也會出問題。`popUntil` 才是「回到某個畫面」的正確做法。
</details>

<details>
<summary>歷史資料為什麼不放進 UiModel？</summary>

32 圈 × N 筆活動是**儲存體**等級的資料，不是每幀的顯示狀態。全部放進快照會浪費 RAM，每幀複製也太貴。所以改用唯讀查詢介面，一次 copy-out 一筆。真手錶上，`activityAt` 會從 Flash 讀 FIT 檔的檔頭。
</details>
